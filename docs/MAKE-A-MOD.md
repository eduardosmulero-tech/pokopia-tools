# Make a mod: from your own file to a package

**Who this is for:** someone who owns the game, has a copy of its files on disk, and has
something they want to change. No previous knowledge of this repository.

**What you end up with:** a folder with a `mod.json` and your own file, turned into a
`.pkmod` package that [INSTALL-AND-DIAGNOSE.md](INSTALL-AND-DIAGNOSE.md) puts in front of the
game.

**What this repository will not do:** it does not include the game, its keys, its text or its
assets, and it does not ship a mod with game content inside. Everything below works on
**your own copy**, and every example file is generated by the scripts in this repository.

## 0. Before you start

* **Python 3.11** (`python --version`); the supported interpreter is declared in
  `pyproject.toml`.
* The kit unzipped. Every command below is run **from its root** and starts with `python
  pkp.py` (the `pkp` and `pkp.cmd` scripts there are shortcuts to the same entry point).
* **Your own copy of the game files.** The kit supports game version **2.0.1a**, update build
  **655360**. Nothing in this repository replaces a copy you must already own.
* Optional but recommended: point `PKP_ROMFS` at the folder with your `LD_C0_R.BIN` and
  `LI_C0_R.IDX` (`export PKP_ROMFS=/path/to/your/romfs`, or pass `--container <folder>`), so
  `validate` can check the mod against your build.

---

## 1. What a mod is here

A mod is **a folder with a `mod.json` manifest and, optionally, your own files**:

```
my-mod/
  mod.json                 mandatory
  payload/...              your files (paths declared in mod.json)
```

There are no scripts inside a mod and nothing is executed. `pkp` reads the manifest, checks
what the manifest *declares* against what is on disk, and writes bytes. Two consequences:

* every edit says **what it expects to find** (`expect`) and **why** (`why`): if the bytes are
  not what you declared, the mod is rejected instead of corrupting a different build;
* the same folder can be re-validated at any time by anyone, without the game.

The format contract, field by field, is [MOD-FORMAT.md](MOD-FORMAT.md). This page is the
practical path through it.

---

## 2. Decide which kind of mod you are making

| You want to change | What you write | Where it is delivered |
|---|---|---|
| A numeric field of a table (an item, a name id, a row) | `edits[]` (bytes) or `text[]` (strings) | `pkp mod apply` on a **copy** of `LD_C0_R.BIN`/`LI_C0_R.IDX`, then that copy is your overlay payload |
| A whole file of the game's romfs (the container, a `.fdata`, a bank) | `romfs[]` (replace file at a path) | `pkp mod pack` → `pkp mod install` (the overlay; nothing is repacked) |

Why the second row matters for textures and audio: this game has **no loose textures or
sounds in its romfs**. The `G1T` textures live inside `LD_C0_R.BIN` (entries #5879–#5948) and
the audio inside `ASRS/KTSR` banks. A texture or sound mod is therefore *a modified container
or `.fdata` file*, delivered as a whole-file replacement. The tools that produce it are
`pkp tex`, `pkp snd` and `pkp anim` (see the format pages those commands print).

If your mod only changes table bytes, you do **not** need the overlay: `pkp mod apply` edits a
copy and prints the undo command. See §5 of [MOD-FORMAT.md](MOD-FORMAT.md).

## 3. A five-minute example (payload generated by us)

The example mod replaces one romfs path with 23 bytes of our own text. It is deliberately not
a valid asset: its job is to show the circuit — manifest, validation, package — without your
dump and without game content in the repository.

```bash
python pkp.py mod example build/mi-mod
```

If you have `PKP_ROMFS` (or a `romfs/` folder next to the kit), the example copies that
container's MD5s, so `validate` checks it against your own build; with no copy at hand it
writes zeros and says so.

```
mod de ejemplo: …/build/mi-mod
  mod.json
  payload/motor_asset_re/KIDS_PLATFORM_OUNCE/system.rdx  (23 B nuestros)
  romfs[0].path = motor_asset_re/KIDS_PLATFORM_OUNCE/system.rdx

siguiente paso:
  python pkp.py mod validate build/mi-mod
  python pkp.py mod pack build/mi-mod --img <RomFS.img>

los md5 del contenedor son ceros: no hay copia configurada (PKP_ROMFS)
ni se paso --container; con un contenedor real `validate` los compararia
```

The manifest it writes:

```json
{
  "mod_format": 1,
  "name": "ejemplo-overlay",
  "version": "0.1.0",
  "authors": ["tu nombre"],
  "description": "Ejemplo generado por `pkp mod example`: …",
  "game": {"title": "pokopia", "version": "2.0.1a",
           "container_md5": {"LD_C0_R.BIN": "000…", "LI_C0_R.IDX": "000…"}},
  "requires": [], "edits": [], "text": [], "files": [],
  "romfs": [{
    "path": "motor_asset_re/KIDS_PLATFORM_OUNCE/system.rdx",
    "file": "payload/motor_asset_re/KIDS_PLATFORM_OUNCE/system.rdx",
    "why": "ejemplo: demuestra el circuito del overlay sin tocar el img"
  }]
}
```

> The two `container_md5` values in the generated example are zeros, because the script does
> not need your dump. For a real mod run `python pkp.py mod new <name>`, which fills them from
> your copy, or pass `--container <folder>` to the example script.

## 4. Put your own file in place

Replace the generated `payload/...` file with **your** file, keeping the same relative path.
A real texture mod looks like this:

```
mi-textura/
  mod.json
  payload/LD_C0_R.BIN        <- your copy with the texture replaced (pkp tex inject …)
```

`romfs[].file` is the path **inside the mod**; `romfs[].path` is the path **inside the game's
romfs**. They do not have to be equal:

```json
{"path": "LD_C0_R.BIN", "file": "payload/contenedor-editado.bin", "why": "textura #5879 propia"}
```

Rules for both paths (`validate` enforces them): relative, `/` as separator, no leading `/`,
no `..`, no drive letter, no empty segment, no duplicate `path`.

Leave `size`, `sha256` and `original_sha256` **out** unless you want them checked early:
`pack` fills all three (the last one from your `RomFS.img`), and that is what proves later
that uninstall restores the original.

## 5. Validate before packing

```bash
python pkp.py mod validate build/mi-mod
```

```
mod: ejemplo-overlay@0.1.0  (0 ediciones de bytes, 0 de texto, 1 fichero(s) de overlay)
  contenedor: (no comprobado)
  img: (sin --img: no se comprueban los original_sha256)
[aviso] sin contenedor: no se ha comprobado container_md5 ni expect
resultado: OK (0 errores, 1 avisos)
```

With the dump available (`export PKP_ROMFS=/path/to/your/romfs`, or `--container <folder>`),
the same command checks the `game.container_md5` against your files and the `expect` of every
byte edit against the real payload. That is the difference between "the file parses" and "this
mod was written for the build you have".

The messages you are most likely to see, and what they mean:

| Message contains | Cause | Fix |
|---|---|---|
| `falta 'expect'` / `'expect' es obligatorio` | a byte edit does not say what was there | read the field on your build and declare it |
| `'why' es obligatorio` | an edit does not say which field it touches | name the field, even if it is a guess |
| `mod.container_md5` / `otro contenedor` | the mod was written for another build | rebuild it against your copy |
| `offset … se sale del stride` | the edit lands outside the row | check the table geometry |
| `no puede llevar '..'` / `separador` | an unsafe romfs path | use relative `/` paths |
| `'mod_format' es N` | a manifest from a newer format | this kit reads `mod_format: 1` only |

Exit code is `0` when the mod is valid, non-zero otherwise, so it can gate a release.

## 6. Pack it

```bash
python pkp.py mod pack build/mi-mod -o build/pkmod --img <RomFS.img>
```

```
mod: ejemplo-overlay@0.1.0
img: …/RomFS.img
  cubre             23 B  sha256 66b4b919021f…  ruta motor_asset_re/KIDS_PLATFORM_OUNCE/system.rdx
                           original 05784a71f65e
paquete: …/build/pkmod/ejemplo-overlay-0.1.0.pkmod
sha256 : 9426635ebdca80bfd03c28c1fb3df97f1a71f5e502efce751bef1877b4b7d543
```

* `cubre` — the path inside the game's romfs that your file replaces.
* `sha256` (per file) — the hash of your file; `install` refuses if the file changed after packing.
* `original` — what the `img` serves at that path **today**. It is written into the package and
  it is the only thing that lets `uninstall` prove the original came back.
* `sha256` (last line) — the package as a whole. It depends on the image, because `original` is
  read from it: the value above is the one the synthetic image in `tools/demo_doctor.py` produces
  (`python tools/demo_doctor.py --conservar` leaves it at `build/demo-doctor/RomFS-A.img`; pack
  with `--img build/demo-doctor/RomFS-A.img` and you get exactly this file). With your own
  `RomFS.img`, every byte of the package is the same except `original_sha256`, so the package hash
  changes with your build.

The package is a deterministic ZIP: the same folder and the same `img` produce the same
`sha256`, byte for byte (two packs of the same input compared in the test suite). Inside it:
your `mod.json` with the three hashes filled, and your files at their relative paths.

---

## 7. What you have, and what is next

`build/pkmod/ejemplo-overlay-0.1.0.pkmod` is an installable mod. It is **not** applied to
anything yet: nothing has touched your game files.

* To put it in front of the game without repacking anything: **[INSTALL-AND-DIAGNOSE.md](INSTALL-AND-DIAGNOSE.md)**.
* To edit table bytes instead of replacing a whole file: `pkp mod apply` on a copy, §5 of
  [MOD-FORMAT.md](MOD-FORMAT.md).

**Before you publish a mod:** a `.pkmod` that carries `LD_C0_R.BIN`, a `.fdata` or any other
file of the game **is game content** and must not go into a public repository. Publish the
manifest and the instructions, not the dump; the repository's publication rule is the same
one that keeps this kit free of game content.
